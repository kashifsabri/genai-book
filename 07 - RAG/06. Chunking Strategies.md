
## Introduction

In the previous chapters, we learned that:

- Documents are loaded.
- Documents are converted into embeddings.
- Similarity Search finds the most relevant chunks.

But we skipped one very important question.

> **What exactly is a chunk?**

Should we create one embedding for an entire PDF?

Or should we split the PDF into smaller pieces?

The answer is **Chunking**.

Chunking is one of the most important parts of a RAG system.

Even the best LLM cannot answer correctly if the documents are chunked poorly.

---

# 6.1 What is Chunking?

Chunking is the process of breaking a large document into smaller pieces.

These smaller pieces are called **Chunks**.

Example:

Original Document

```text
Employee Handbook

• Company Introduction
• Leave Policy
• Working Hours
• Dress Code
• Remote Work Policy
```

After Chunking

```text
Chunk 1

Company Introduction
```

```text
Chunk 2

Leave Policy
```

```text
Chunk 3

Working Hours
```

```text
Chunk 4

Dress Code
```

```text
Chunk 5

Remote Work Policy
```

Instead of searching one huge document,

the RAG system searches these smaller chunks.

---

# 6.2 Why Can't We Store the Entire PDF?

Imagine your Employee Handbook has:

```text
300 Pages
```

Now the user asks:

```text
How many paid leave days do employees receive?
```

Should we send all 300 pages to the LLM?

No.

Problems:

- Slow
- Expensive
- Wastes tokens
- Most pages are unrelated

Instead,

we retrieve only the relevant chunk.

For example:

```text
Employees receive 24 paid leave days every year.
```

This is much faster and more accurate.

---

# 6.3 What Happens If Chunks Are Too Large?

Suppose we create chunks like this.

```text
Chunk Size

100 Pages
```

Now one chunk contains:

- Company History
- Leave Policy
- Dress Code
- Payroll
- Holidays
- IT Policy

When retrieved,

the LLM receives a lot of unnecessary information.

This increases:

- Cost
- Latency
- Confusion

Large chunks reduce retrieval quality.

---

# 6.4 What Happens If Chunks Are Too Small?

Now suppose we split every sentence.

Example:

```text
Employees receive
```

```text
24 paid leave days
```

```text
every year
```

Now the information is broken apart.

The complete meaning is lost.

The retriever may return only:

```text
24 paid leave days
```

The LLM no longer has enough context.

Small chunks also reduce retrieval quality.

---

# 6.5 Finding the Right Chunk Size

There is no perfect chunk size.

It depends on:

- Document type
- LLM Context Window
- Use case

General guideline:

| Document Type | Suggested Chunk Size |
|--------------|---------------------:|
| FAQs | 200–400 characters |
| Articles | 500–1000 characters |
| Technical Documentation | 800–1500 characters |
| Books | 1000–2000 characters |

These are starting points.

Always experiment with your own data.

---

# 6.6 Chunk Overlap

Imagine this sentence.

```text
Employees receive 24 paid leave days every year.

Unused leave can be carried forward.
```

Suppose we split exactly in the middle.

Chunk 1

```text
Employees receive 24 paid leave days
```

Chunk 2

```text
every year.

Unused leave can be carried forward.
```

The sentence has been broken.

To solve this,

we use **Chunk Overlap**.

Example:

```text
Chunk Size = 500

Overlap = 100
```

The last 100 characters of one chunk are copied into the next chunk.

Example:

Chunk 1

```text
...24 paid leave days every year.
```

Chunk 2

```text
24 paid leave days every year.

Unused leave can be carried forward.
```

Now the context is preserved.

---

# 6.7 Types of Chunking

There are several chunking strategies.

The most common are:

- Fixed-Size Chunking
- Recursive Chunking
- Semantic Chunking

Let's understand them.

---

# 6.8 Fixed-Size Chunking

This is the simplest approach.

The document is split after a fixed number of characters.

Example:

```text
500 characters

↓

New Chunk

↓

500 characters

↓

New Chunk
```

Advantages:

- Simple
- Fast

Disadvantages:

- Can split sentences
- Can split paragraphs

---

# 6.9 Recursive Chunking

Instead of splitting blindly,

Recursive Chunking tries to preserve the document structure.

It first tries to split by:

- Headings
- Paragraphs
- Sentences

Only if necessary does it split into smaller pieces.

This is why Recursive Chunking is the most popular strategy in LangChain.

---

# 6.10 Semantic Chunking

Semantic Chunking is more advanced.

Instead of looking at characters,

it looks at **meaning**.

If two paragraphs discuss the same topic,

they stay together.

If the topic changes,

a new chunk is created.

This usually produces better retrieval results,

but it is slower.

---

# 6.11 Python Example (LangChain)

Install the package.

```bash
pip install langchain-text-splitters
```

Import the splitter.

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter
```

Create the splitter.

```python
text_splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=100
)
```

Example document.

```python
text = """
Employees receive 24 paid leave days every year.

Unused leave can be carried forward.

Office timings are from 9 AM to 6 PM.
"""
```

Split into chunks.

```python
chunks = text_splitter.split_text(text)

for chunk in chunks:
    print(chunk)
```

LangChain automatically creates overlapping chunks.

---

# 6.12 Which Chunking Strategy Should I Use?

| Strategy | Best For |
|----------|----------|
| Fixed-Size | Learning and simple projects |
| Recursive | Most RAG applications |
| Semantic | High-quality production RAG |

For this book,

we'll use:

```text
RecursiveCharacterTextSplitter
```

because it provides an excellent balance between simplicity and retrieval quality.

# Real-World Example

Imagine moving a large book.

Instead of tearing out random pages,

you separate it chapter by chapter.

Each chapter still makes sense on its own.

Chunking works in the same way.

The goal is not just to split the document.

The goal is to preserve meaning while making retrieval efficient.

# Common Beginner Mistakes

### Mistake 1

Thinking smaller chunks are always better.

Very small chunks often lose important context.

---

### Mistake 2

Thinking larger chunks are always better.

Very large chunks include too much unrelated information.

---

### Mistake 3

Ignoring chunk overlap.

Without overlap, important information may be split across chunks.

---

# Key Takeaways

- Chunking splits large documents into smaller pieces.
- Good chunking improves retrieval quality.
- Chunk overlap helps preserve context between chunks.
- Recursive Chunking is the most commonly used strategy in LangChain.
- Choosing the right chunk size is one of the most important decisions when building a RAG system.
