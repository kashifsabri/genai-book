

## Introduction

In the previous chapter, we learned how to evaluate a RAG system using concepts like:

- Precision
- Recall
- Hit Rate
- Hallucination Detection

These metrics are useful.

But evaluating RAG systems manually becomes difficult as the number of questions grows.

Modern AI teams use specialized evaluation frameworks.

One of the most popular is **RAGAS**.

RAGAS automatically measures the quality of a RAG system without requiring manually labeled answers for every question.

---

# 18.1 What is RAGAS?

**RAGAS** stands for:

```text
Retrieval-Augmented Generation Assessment
```

It is an open-source framework designed specifically for evaluating RAG systems.

Instead of checking only whether the answer looks good,

RAGAS evaluates:

- Was the correct context retrieved?
- Is the answer supported by the retrieved context?
- Did the LLM hallucinate?
- Is the answer relevant to the question?

---

# 18.2 Why Do We Need RAGAS?

Imagine you have built a chatbot for your company.

You have:

- 5,000 documents
- 500 test questions

Will you manually read every answer?

Probably not.

RAGAS automates this evaluation.

Instead of manually checking hundreds of answers,

it calculates useful evaluation scores.

---

# 18.3 How RAGAS Works

A RAG system produces four things.

```text
Question

↓

Retrieved Context

↓

Generated Answer

↓

Reference Answer (Optional)
```

RAGAS uses these inputs to calculate different evaluation metrics.

# 18.6 Core RAGAS Metrics

RAGAS provides several evaluation metrics.

Let's understand the most important ones.

---

## Faithfulness

Question:

> Is the generated answer supported by the retrieved context?

Context

```text
Employees receive 24 paid leave days.
```

Answer

```text
Employees receive 30 paid leave days.
```

The answer is **not** supported.

Faithfulness will be low.

A high Faithfulness score means the LLM stayed grounded in the retrieved documents.

---

## Answer Relevancy

Question:

```text
How many leave days do employees receive?
```

Answer

```text
Employees receive 24 paid leave days every year.
```

Very relevant.

Now suppose the answer is:

```text
The company has offices in Mumbai.
```

Although it may be true,

it does not answer the user's question.

Answer Relevancy will be low.

---

## Context Precision

Question:

Did the Retriever return mostly useful documents?

Suppose:

Retriever returns:

```text
10 Documents
```

Only:

```text
8 Documents
```

are actually useful.

Context Precision measures how much of the retrieved context is relevant.

Higher is better.

---

## Context Recall

Question:

Did the Retriever miss important documents?

Suppose:

Five relevant documents exist,

but only three were retrieved.

Context Recall becomes lower.

Higher Recall means fewer important documents were missed.

---

# 18.7 Summary of Metrics

| Metric | Measures |
|---------|----------|
| Faithfulness | Is the answer supported by the retrieved context? |
| Answer Relevancy | Does the answer actually answer the question? |
| Context Precision | Are the retrieved documents relevant? |
| Context Recall | Were important documents retrieved? |

These four metrics are the ones you'll use most often.

# 18.11 Mini Project

## Goal

Evaluate your RAG chatbot.

Steps:

1. Create 20–30 test questions.
2. Run each question through your RAG system.
3. Save:
   - Question
   - Retrieved Context
   - Generated Answer
4. Run RAGAS evaluation.
5. Review the scores.

If a metric is consistently low, investigate why:

- Is chunking poor?
- Are embeddings unsuitable?
- Is the retriever missing documents?
- Is the prompt causing hallucinations?

---

# 18.12 When Should You Use RAGAS?

Use RAGAS when:

- Testing a new RAG system.
- Comparing different embedding models.
- Comparing chunking strategies.
- Comparing retrievers.
- Measuring improvements after changing prompts or retrieval settings.

It provides an objective way to compare different RAG pipelines.

# Common Beginner Mistakes

### Mistake 1

Thinking a high-quality answer means the retriever performed well.

A good answer can still be based on poor retrieval or luck.

Evaluate retrieval and generation separately.

---

### Mistake 2

Using only one evaluation metric.

A complete evaluation should consider retrieval quality and answer quality together.

---

### Mistake 3

Evaluating only a few example questions.

A small sample can hide weaknesses.

Use a diverse evaluation dataset that covers different document types and question styles.
