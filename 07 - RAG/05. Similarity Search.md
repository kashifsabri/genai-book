

## Introduction

In the previous chapter, we learned that both documents and user questions are converted into embeddings.

Now another question arises.

Suppose your Vector Database contains **1 million embeddings**.

How does the system know which document is most relevant?

The answer is **Similarity Search**.

Similarity Search compares the embedding of the user's question with the embeddings stored in the Vector Database.

The embeddings that are most similar are returned.

---

# 5.1 What is Similarity Search?

Similarity Search is the process of finding vectors that are **closest in meaning** to the user's query.

Suppose we have three document chunks.

```text
Chunk 1

Employees receive 24 paid leave days every year.
```

```text
Chunk 2

Office timings are 9 AM to 6 PM.
```

```text
Chunk 3

Employees can work remotely two days a week.
```

Now the user asks:

```text
How many leave days do employees receive?
```

The system should retrieve:

```text
Chunk 1
```

because it is the most similar.

---

# 5.2 How Does Similarity Search Work?

The process is simple.

```text
User Question
      │
      ▼
Generate Embedding
      │
      ▼
Compare with Every Stored Embedding
      │
      ▼
Calculate Similarity Score
      │
      ▼
Return the Most Similar Chunks
```

The chunk with the highest similarity score is considered the best match.

---

# 5.3 Example

Suppose the similarity scores are:

| Chunk | Similarity Score |
|--------|-----------------:|
| Leave Policy | 0.95 |
| Working Hours | 0.32 |
| Company History | 0.18 |

The retriever returns:

```text
Leave Policy
```

because it has the highest score.

---

# 5.4 Why Not Compare Plain Text?

Imagine these two questions.

Question 1

```text
How do I reset my password?
```

Question 2

```text
I forgot my password.
```

The wording is different.

A keyword search may treat them as different.

Embedding-based similarity understands that they have almost the same meaning.

This is why modern RAG systems use embeddings instead of plain text matching.

---

# 5.5 Similarity Metrics

A **Similarity Metric** is a mathematical method used to compare two embeddings.

The three most common metrics are:

- Cosine Similarity
- Dot Product
- Euclidean Distance

Let's understand each one.

---

# 5.6 Cosine Similarity

Cosine Similarity is the most commonly used metric in RAG.

It compares the **direction** of two vectors.

Imagine two arrows.

```text
Arrow A

────►
```

```text
Arrow B

────►
```

Both arrows point in the same direction.

Their similarity is very high.

Now imagine this.

```text
Arrow A

────►
```

```text
Arrow B

▲
```

They point in different directions.

Their similarity becomes lower.

In simple words,

Cosine Similarity checks whether two embeddings point in the same direction.

The more similar the direction,

the more similar the meaning.

---

# 5.7 Dot Product

Dot Product also measures similarity,

but it considers both:

- Direction
- Magnitude (length)

Some embedding models are specifically trained to use Dot Product.

You usually don't need to choose this yourself.

The embedding model documentation tells you which metric works best.

---

# 5.8 Euclidean Distance

Euclidean Distance measures the straight-line distance between two vectors.

Think about two cities.

```text
City A ---------------- City B
```

If the cities are close,

the distance is small.

If they are far apart,

the distance is large.

Embeddings work the same way.

Smaller distance usually means more similar meaning.

---

# 5.9 Which Metric Should I Use?

Most of the time,

you don't have to decide manually.

The Vector Database or embedding model already recommends the correct metric.

As a general rule:

| Metric | Common Usage |
|---------|--------------|
| Cosine Similarity | Most RAG applications |
| Dot Product | Some embedding models |
| Euclidean Distance | Mathematical comparisons |

For this book,

we'll mainly use **Cosine Similarity**.

---

# 5.10 Python Example (Cosine Similarity)

Install the required library.

```bash
pip install scikit-learn
```

Example:

```python
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

model = SentenceTransformer(
    "all-MiniLM-L6-v2"
)

sentence1 = model.encode(
    "Employees receive 24 paid leave days."
)

sentence2 = model.encode(
    "How many vacation days do employees get?"
)

score = cosine_similarity(
    [sentence1],
    [sentence2]
)

print(score)
```

Possible Output

```text
[[0.91]]
```

A score closer to **1** means the meanings are very similar.

## 5.11 Using LangChain

Let's see how Similarity Search works using LangChain.

First, install the required libraries.

```bash
pip install langchain
pip install langchain-community
pip install langchain-huggingface
pip install langchain-chroma
pip install sentence-transformers
```

Import the required classes.

```python
from langchain_huggingface import HuggingFaceEmbeddings
from langchain_chroma import Chroma
```

Create an embedding model.

```python
embeddings = HuggingFaceEmbeddings(
    model_name="sentence-transformers/all-MiniLM-L6-v2"
)
```

Suppose we have three documents.

```python
documents = [
    "Employees receive 24 paid leave days every year.",
    "Office timings are 9 AM to 6 PM.",
    "Employees can work remotely twice a week."
]
```

Create a Vector Store.

```python
vector_store = Chroma.from_texts(
    texts=documents,
    embedding=embeddings
)
```

Now search for similar documents.

```python
results = vector_store.similarity_search(
    query="How many vacation days do employees get?",
    k=3
)
```

Print the results.

```python
for document in results:
    print(document.page_content)
```

Possible Output

```text
Employees receive 24 paid leave days every year.

Employees can work remotely twice a week.

Office timings are 9 AM to 6 PM.
```

Notice that we never compared the text manually.

LangChain automatically:

1. Converts the query into an embedding.
2. Searches the Vector Store.
3. Calculates similarity.
4. Returns the most relevant documents.

# 5.12 Mini Project — Semantic Search

Let's build a simple semantic search application.

## Goal

Find the most similar sentence from a list of documents.

---

### Step 1 — Install Libraries

```bash
pip install sentence-transformers
pip install scikit-learn
```

---

### Step 2 — Create Documents

```python
documents = [
    "Employees receive 24 paid leave days every year.",
    "Office timings are 9 AM to 6 PM.",
    "Employees can work remotely twice a week."
]
```

---

### Step 3 — Generate Embeddings

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer(
    "all-MiniLM-L6-v2"
)

document_embeddings = model.encode(documents)
```

---

### Step 4 — User Question

```python
query = "How many vacation days do employees receive?"

query_embedding = model.encode(query)
```

---

### Step 5 — Calculate Similarity

```python
from sklearn.metrics.pairwise import cosine_similarity

scores = cosine_similarity(
    [query_embedding],
    document_embeddings
)
```

---

### Step 6 — Find the Best Match

```python
best_match = scores.argmax()

print(documents[best_match])
```

Output:

```text
Employees receive 24 paid leave days every year.
```

Congratulations!

You have just built a very simple semantic search engine.

This is one of the core ideas behind every RAG system.

# Common Beginner Mistakes

### Mistake 1

Thinking Similarity Search compares plain text.

It compares embeddings, not raw text.

---

### Mistake 2

Thinking the highest similarity score always guarantees the perfect answer.

Similarity Search retrieves the most relevant chunks, but the quality also depends on the embedding model and chunking strategy.

---

### Mistake 3

Thinking every Vector Database uses the same similarity metric.

Different databases and embedding models may use different metrics.
